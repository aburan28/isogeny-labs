A 29-year-old challenge got four times cheaper, and the math didn't change

GPU cryptanalysis · parallel Pollard rho · CUDA

In 1997, Certicom posted a set of challenges: here are some elliptic curves, here are some public keys, go find the private ones. Most are still unsolved. The cheapest is ECC2K-130, and it has been open for 29 years.

We did not solve it. What we did was make the standard attack run 17.1 times faster on a single NVIDIA RTX PRO 6000 Blackwell. The algorithm is untouched. It takes exactly as many steps as it always did. Every bit of the gain is in how the arithmetic is arranged on the GPU.

At the old speed, the attack needs roughly 80 GPU-years on one card. At the new speed, about 4.7.

Before going further, we should be clear about what this does and does not mean. ECC2K-130 is a small challenge curve chosen in 1997 precisely because it was the cheapest unsolved target. Nobody deploys it. Nothing you are using today is weaker than it was last week. We found no mathematical break and we are not claiming one.

What we think is interesting is the gap itself: a published security estimate moved by a factor of 17 without anyone discovering anything new about elliptic curves.

What the attack does, and where the time goes

The attack is a search. You start a few million walks at random points on the curve and step them forward. Eventually two walks land on the same point, and that collision hands you the answer. There is no cleverness available: the number of steps is fixed by mathematics. The only thing you can change is how fast each step runs.

Each step is dominated by one expensive operation, a kind of multiplication. Count it up and you conclude this is a multiplication problem. Implementations have assumed that for fifteen years, and we assumed it when we started.

We were wrong. The chip was running at about 6% of what it can do, and the multiplier was not the reason. Each thread's working data had spilled out of the chip's fast internal storage into slow memory, and the machine was spending its time waiting.

Three changes carried most of it

Sixteen changes took us from 0.86 to 14.64 billion steps per second. Three did the heavy lifting.

Making the data fit. The old code stored each number spread across 131 slots, so a thread needed 16KB of working space — far more than the fast storage a GPU thread gets. We repacked it into five slots. Identical mathematics, same results, but now the thread's data stays in the fast storage instead of spilling to memory. Worth 3.47× on its own.

Doing ten shuffles in one pass. The attack repeatedly performs an operation that, under the old layout, was free. Under the new layout it costs a bit-shuffle, and the attack does up to ten in a row. We replaced the ten shuffles with a single fixed wiring pattern that produces the same result in one pass. Another 41%.

Using the instruction the chip already has. This attack needs a specific flavor of multiplication, and NVIDIA's newest chips have a dedicated instruction for it. The old code emulated it with 144 ordinary multiplies. Six instructions now do the same work. That was worth 22%, and because multiplication suddenly got cheap, retuning how the work is batched was worth another 52%.

After all of it, the bottleneck has moved. The chip is no longer waiting on memory or on multiplication, it is running its general-purpose arithmetic at 91% of capacity.

The part that surprised us

Here is the finding we did not expect, and the one we think is useful beyond this problem.

That is more than a tenfold swing in the relative price of two operations, across cards from one vendor in one generation. On the RTX PRO 6000 the carry-less unit is the scarce resource and you avoid using it. On a B200 that unit sits idle and the general arithmetic becomes the bottleneck instead, so the advice reverses.

The consequence is concrete. Two changes we built, measured, and rejected on the RTX PRO 6000 turn out to win on a B200, one of them by 37.9% when combined with related changes.

This is why we publish what failed alongside what worked. A list of successful optimizations tells you nothing about hardware you have not tested. A model of where the time goes does, and ours predicted the B200 reversal before we measured it.

Why this matters

Every system that uses cryptography is being rewritten right now. The post-quantum algorithms are settled, and the deadlines are real: new national security systems must support them from 2027, with older systems phased out by 2030.

What is not settled is everything downstream of the standard.

Implementation quality moves security by factors that matter. We moved the cost of one attack by 17 times without touching any mathematics. Every post-quantum implementation being written right now is new code, much of it on constrained hardware, under schedule pressure, by teams doing this for the first time. The distance between what a specification promises and what the code delivers is where the risk lives, and almost nobody measures it.

Published security estimates are the weakest input to a migration plan. Those numbers get used to choose parameters, and they move. Germany's federal cybersecurity agency recommended a scheme called Classic McEliece for six years and withdrew that recommendation in September 2026, after new analysis dropped its estimated attack cost from far out of reach to below the required level. No deployment changed. The number did.

This is what crypto agility is for. If a security estimate can move by an order of magnitude from engineering alone, and further from new mathematics, then being able to swap algorithms quickly is part of the security of the system. Measurement is what tells you when to use it.

The last serious GPU implementation of this attack was published in 2010, on hardware that did not have the instruction that made the biggest difference here. The approach that was fastest then is not the fastest now, and nobody had checked, because checking is unglamorous engineering rather than mathematics.

That gap is what we built this lab to measure.

How we measured it

Every improvement is a paired comparison: the old version and the new version run alternately on the same card, in the same session, and we take the middle of three samples. Each sample runs between 100 and 200 billion steps.

Correctness is checked four ways, and the last one is the one that matters: the faster version has to produce exactly the same output as the original, with nothing missing. A speedup that changes a single result is rejected, not investigated. We also run the whole pipeline against a smaller challenge that was solved in 1998, where the answer is public, to confirm the entire system works end to end.

The code, the build options and the measurement records are public. One command runs the validation and the benchmarks. If you have the card, you can check our number yourself.

What is next

Two further improvements are built but not yet timed, and our model predicts about 21.5 billion steps per second from them.

The more interesting one is the B200. Our model says two optimizations we rejected should win there, one substantially. We have not been able to test it.

We would also like to try this on FPGAs, a different kind of chip that suits this math well. Our estimate is that one FPGA would be competitive with one GPU on speed and five to ten times better per watt. That is an estimate, not a measurement, and it is the next thing we want to check.
