Schemes / Signatures

ECDSA

ECDSA signs TLS certificates, hardware tokens and cryptocurrency transactions. Nobody has come close to solving the elliptic-curve discrete logarithm behind it, yet ECDSA keys are lost regularly, and almost always the same way: through the random number used once per signature.

Rests on
The ECDLP, and a uniformly random secret nonce for every signature
Standards
FIPS 186-5; SEC 1; ANSI X9.62; deterministic nonces in RFC 6979
Sizes
P-256: 64-byte signature (r, s); 33-byte compressed public key
Best known attack
Pollard's rho on the curve, about 2128 for P-256. In practice, reused, biased or leaked nonces
Quantum
Broken by Shor's algorithm

Signing and verifying

The public parameters are a curve with a base point G of prime order n. A private key is an integer d, and the public key is Q = dG. To sign a message, hash it to an integer z, then:

  1. Choose a secret nonce k uniformly between 1 and n − 1.
  2. Compute the point kG and let r be its x-coordinate mod n.
  3. Compute s = k−1(z + rd) mod n. The signature is (r, s).

To verify, compute w = s−1, then the point (zw)G + (rw)Q, and accept if its x-coordinate mod n equals r. It works because (zw)G + (rw)Q = w(z + rd)G = kG.

The example on this page runs on the real P-256 curve, at full size, in the code that builds this page. A key pair was drawn, and the message "Pay Alice 10 coins" was signed with a random nonce:

It verifies against Q, and does not verify for "Pay Bob 20 coins".

One nonce, two signatures

Look at the signing equation as an attacker would. It is one linear equation, s = k−1(z + rd), in two unknowns, k and d. A single signature reveals nothing, because every d has a matching k. But if the same k is ever used for two messages, the two signatures share r and give two equations in the same two unknowns:

k = (z1 − z2) / (s1 − s2),   d = (s1k − z1) / r  (mod n) Two signatures with the same nonce give up the private key

The build signed "Pay Alice 10 coins" and "Pay Bob 20 coins" with the same nonce. Both signatures are valid, and both have the same r, which is how the reuse is spotted from outside:

The recovered d satisfies dG = Q, so it is the private key. The build then signs "Pay Mallory everything" with it, and that signature verifies under the victim's public key. There is no search here and no dependence on the curve's size: two modular inversions and a few multiplications break the key.

This has happened in production. In 2010 the fail0verflow group showed that Sony signed PlayStation 3 software with a fixed nonce, and recovered the signing key. In 2013 a flaw in Android's SecureRandom caused Bitcoin wallets to repeat nonces, and coins were taken from the affected addresses. Scanning public blockchains for repeated r values still turns up keys.

Deterministic nonces

The standard fix is to stop needing a random number generator at signing time. RFC 6979 derives k deterministically from the private key and the message hash with HMAC. The same message always gets the same nonce, and different messages get unrelated ones. Repeating k across different messages then needs an HMAC collision. EdDSA builds the same idea into its definition, and FIPS 186-5 allows deterministic ECDSA.

Deterministic signing has a weakness of its own. Because the same computation happens every time, a fault injected during one signing can be compared with a correct signature on the same message, and similar fault attacks work much as they do on RSA with CRT. Hedged signing, which mixes fresh randomness into the deterministic derivation, keeps the protection against bad generators while defeating these comparisons. It is the default in ML-DSA.

Biased and leaked nonces

The nonce does not have to repeat to be fatal. Each signature gives a linear relation between k and d. If an attacker knows a few bits of each k, from a timing side channel, a biased generator or a truncated random number, many signatures together form an instance of the hidden number problem, which lattice reduction solves. Published attacks recover P-256 and secp256k1 keys from nonce leaks of a few bits per signature, given enough signatures. Constant-time scalar multiplication and nonces drawn uniformly mod n, not reduced from a slightly shorter string, are what prevents this.

Malleability

If (r, s) is a valid signature, so is (r, n − s): negating s negates w, and the verification point becomes −kG, which has the same x-coordinate. For the signature above, n − s is

s'  = 258958cb80f2375e4fafcba9305c2a699c2dcde5c3d873866c4a54ac4cba7b69

The second valid signature on the same message, under the same key

and it verifies. This does not let anyone sign a new message, but it breaks any system that identifies a signed object by the hash of its signature. Bitcoin transaction identifiers had exactly that problem, and Bitcoin now requires the smaller of s and n − s. EdDSA and Schnorr signatures as in BIP-340 are defined so that this does not arise.

Where it stands

Against the curve itself ECDSA is as strong as the ECDLP, about 2128 for P-256 and secp256k1; see the ECDLP note. Against a quantum computer running Shor's algorithm it falls completely, and NIST IR 8547 proposes disallowing it after 2035. Until then, reviewing an ECDSA implementation is mostly reviewing its nonces: where they come from, whether they are uniform mod n, and whether they leak through timing.
