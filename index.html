Isogeny Labs

We work out what it costs to break public-key cryptography, mostly elliptic-curve and isogeny-based systems, and we check our estimates by running the attacks.

Most of this work is public. The code is on GitHub, benchmarks are published with the commands that produced them, and the figures below can be reproduced on your own hardware. We take on client work in the same areas: parameter and hardness reviews, implementations, protocol audits, and post-quantum migration.

Current work

  1. ECC2K-130

    Ongoing · distributed Pollard rho · CUDA, Metal, CPU

    Certicom's ECC2K-130 challenge is a discrete logarithm on a Koblitz curve over GF(2131). It has been unsolved since Certicom published it in 1997. We are running a distributed Pollard rho walk against it, and have written walk clients for NVIDIA GPUs, Apple GPUs, and ARM CPUs. Each client's arithmetic is tested bit for bit against a reference model, and any point a client reports can be re-walked from its seed.

  2. A discrete-log library that measures its own constants

    C11 · Rust, Go and Python bindings

    Baby-step giant-step, Pollard rho and kangaroo, Bernstein–Lange precomputation, Pohlig–Hellman, Cheon's attack, a linear-sieve index calculus, a distributed rho coordinator, and a CUDA rho kernel. Every solver reports its work as S = group operations / √n, so two algorithms, or two implementations of the same one, can be compared directly. Groups are capped at 64 bits on purpose: the library is for measuring algorithms, not for attacking deployed keys.

Services

Hardness and parameter review
You have a curve, an isogeny parameter set, or a custom group, and you need a security level you can defend. We estimate the cost of the best known attack, and where the numbers are close we run a scaled-down version to check the estimate.
Elliptic-curve and isogeny implementations
Reference implementations and test vectors for SQIsign, CSIDH-family schemes, pairings, and curve arithmetic, tested against an independent model rather than against themselves.
Post-quantum migration
Finding where your systems depend on RSA and elliptic curves, planning a hybrid move to ML-KEM and ML-DSA, and working out how to roll back if interoperability breaks partway.
Protocol and implementation review
The protocol, its security proof if it has one, and the code: nonce generation, key handling, and side channels. Findings are ranked by how exploitable they are.

Each engagement starts with a written scope that names the system, the adversary, and what would count as a break. At the end you get a report and any code we wrote, and the code runs without us.
